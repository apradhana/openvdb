4) Mesh Manifoldness / Surfacing Discussion

* Ken raised an off-the-record-style discussion stemming from SIGGRAPH paper review feedback.
* Reviewer feedback questioned whether the current OpenVDB meshing approach guarantees manifold output.
* Ken noted that the current OpenVDB meshing tool is apparently **not guaranteed** to generate manifold surfaces.
* Jeff noted this is not entirely new:
  * The current method can also leave holes.
  * Failures can appear when sign changes occur across higher-level tree nodes / tile boundaries.
  * Clipping operations can expose these issues more clearly.
* Team discussed whether this matters in practice:
  * Jeff’s view was that downstream pipelines should generally tolerate non-manifold outputs.
  * However, understanding the limitations is still worthwhile.
* Ken said it would be useful to better characterize:
  * what kinds of non-manifold or open-manifold cases are produced,
  * when they appear,
  * and whether any fixes are worth pursuing.
* Jeff showed an example in Houdini demonstrating holes caused by tile boundaries after clipping.
* Team noted that:
  * Mihai’s adaptation of dual marching cubes to VDB + adaptivity was highly useful,
  * but the method was never fully published or formally documented,
  * and some guarantees from the original uniformly sampled method may not carry over.
* Ken plans to ask Rohan for more detail on what the mesh-analysis tool specifically flagged.

5) External PR Policy (DCO / CLA)

* Dan raised the issue of external PRs arriving without signed DCO / CLA, often then stalling indefinitely.
* This is increasingly relevant as AI-assisted PRs become more common.
* Concerns raised:
  * Review time is wasted on PRs that cannot be merged yet.
  * Maintainers should avoid deeply reviewing unsigned PRs.
  * Unsigned code creates legal / copyright complications even if the change looks correct.
* Proposed policy:
  * When a PR arrives without DCO / CLA, respond immediately with instructions.
  * If the author has not completed the required signing within about **one week**, close the PR.
  * Allow reopening once the paperwork is complete.
* Jeff strongly supported the one-week approach over a month-long grace period.
* Ken suggested drafting a boilerplate response and adding the policy to project documentation.
* Dan suggested the TSC meeting can serve as a periodic point to review and clean up stalled PRs.
* Team agreed the rule should be applied with judgment:
  * If the author is actively trying to complete signing, do not close aggressively.
  * Exception cases with critical bug reports can still be handled separately.

6) GitHub Actions / Security Discussion

* Ken asked about a recent ASWF TAC discussion concerning security, LLMs, and CI.

* Dan said he would double-check, but current understanding is that OpenVDB is not exposed to that specific issue.

9) Doxygen Filename Collision Issue

* Team diagnosed the Doxygen problem more precisely:
  * `openvdb/io/io.h` and `nanovdb/io/IO.h` resolve badly on case-insensitive filesystems.
  * Doxygen flattens generated HTML output into a single directory, causing name collisions.
  * This also creates broader cross-platform issues, especially on Windows/macOS.
* Jeff and Dan discussed possible workarounds, but a direct rename is difficult because of downstream include compatibility.
* Possible direction:
  * create a new replacement header with a new name,
  * leave compatibility shims / deprecation warnings,
  * and eventually transition in a future major release.
* Dan noted this may align naturally with the broader IO refactor anyway.

10) IO API Cleanup Ideas

* Dan said current IO APIs are more cumbersome than they need to be for common file-writing tasks.
* He would like a simpler free-function style API, e.g.:
  * pass a grid and a filename directly,
  * write without manually constructing file/stream objects.
* This may be a good opportunity to move functionality out of the current `io.h` surface and into a cleaner header structure.
* Ken also recommended taking advantage of `std::filesystem` now that C++17 is available.
* Dan noted that much of the older filesystem complexity was tied to delayed loading, and that some of it may disappear as the new IO architecture simplifies.
